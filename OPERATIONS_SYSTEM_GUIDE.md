# TTI Operations System Guide

This guide establishes a concise operating method for turning project plans into verifiable outcomes.

## Operating Rule

> A task is **done** only when the promised result is visible and verifiable. A draft, plan, template, or prepared packet is **prepared**, not done.

## Outcome Delegation Cycle

| Stage | Question | Required record |
| --- | --- | --- |
| Outcome | What specific result is required? | Definition of done, deadline, and owner |
| Preparation | What research, assets, drafts, or technical work can be completed safely? | Evidence folder and prepared work package |
| Release | What requires an account action, authorization, signature, payment, filing, or external commitment? | Explicit release gate and proof of completion |

## Single Command Board

Use one board row per outcome.

| Field | Standard |
| --- | --- |
| Workstream | Revenue, product, operations, compliance, partnerships, career, or systems |
| Outcome | A measurable end state, not an activity |
| Status | Ready, prepared, active, waiting, blocked, or done |
| Constraint | The one current blocker |
| Next action | The smallest legitimate step that removes the blocker |
| Owner | System, account holder, external party, or qualified professional |
| Evidence | File path, receipt, log, response, published URL, or accepted record |
| Release gate | None, external communication, credentials, payment, filing, signature, or contract |

## Priority Order

1. Restore a verified buyer or fulfillment path before expanding new initiatives.
2. Complete prepared assets that reduce delivery friction.
3. Prepare high-value communications and documents with source-backed facts.
4. Maintain a visible queue for account-bound, financial, legal, regulated, and signature-required work.
5. Scale only after the first end-to-end workflow is tested and logged.

## Safe Automation Standard

Automate preparation, reporting, classification, asset generation, and evidence tracking. Do not automate payments, signatures, filings, identity verification, number ports, legal assertions, or regulated-service actions without the required account access and final approval.

## Completion Evidence

| Outcome type | Minimum proof |
| --- | --- |
| Product purchase path | Testable checkout and verified fulfillment |
| External message | Sent record with recipient, context, and outcome log |
| Technical deployment | Published version, smoke test, and change record |
| Filing or account action | Accepted receipt or dashboard confirmation |
| Partnership or sale | Written confirmation and current next step |

## Weekly Cadence

| Cadence | Activity |
| --- | --- |
| Daily | Triage incoming revenue, partner, career, and operating messages; update next actions. |
| Daily | Advance one constraint-removal task with verifiable output. |
| Weekly | Reconcile product, fulfillment, outreach, and evidence records. |
| Weekly | Remove duplicate tasks and stale status claims from the command board. |

This guide is intentionally platform-neutral. It should be used with the current command ledger and evidence records maintained outside the public repository.
